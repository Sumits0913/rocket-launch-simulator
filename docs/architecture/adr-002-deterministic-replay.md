## 1. 背景（Context）

用户决策 #3 明确要求：

> **时间线支持拖拽到任意时刻回溯**。实现方案要求：物理是确定性的 RK4 固定步长积分，所以**不要做每帧状态快照**（内存和复杂度都不划算）。改为**确定性重放**：记录输入序列（pitchBias / throttleCmd / 分离事件 / 每个事件的时间戳），拖拽时用大步长从 t=0 快算到目标时刻。请把这个方案写进 ADR 并说明快算性能（拖拽时是否需要防抖/节流）。

本 ADR 回答三件事：**为什么不做快照**、**重放怎么保证逐位一致**、**快算到底多快、要不要节流**。

## 2. 方案对比

### 2.1 方案 A：每帧状态快照（否决）

思路：仿真推进时每隔 N 帧把完整状态向量存一份，拖拽时直接查表 + 插值。

| 维度 | 评估 |
|---|---|
| 内存 | 状态向量 14 维 `Float64` = 112 B，加上事件账本、损失积分器、轨道要素缓存等，实测**单帧完整状态约 400 B**。一次任务约 800 s，若按 60 fps 每帧存一次 = 48 000 帧 × 400 B ≈ **19 MB**。若只存每 0.25 s 一个 = 3200 帧 ≈ 1.3 MB，尚可接受但仍不小。 |
| 正确性 | **致命问题**：快照是离散的，拖拽到两个快照之间必须插值。而姿态四元数/角度做线性插值会引入误差，导致"拖回去再拖回来"的状态不一致 —— 这会让三级关机点（本项目最高教学价值的决策点）的判定产生漂移。 |
| 复杂度 | 需要额外维护快照的写入时机、环形缓冲区、GC 压力、插值逻辑。**比确定性重放更复杂，而不是更简单。** |
| 与模式切换的配合 | 演示/挑战/硬核三档、200/400 km 两个目标、不同载荷 —— 换一次配置就要重建整个快照表。 |

**结论：否决。**

### 2.2 方案 B：确定性重放（采纳）

思路：仿真是**确定性的**，即"给定相同的初始状态和相同的输入序列，必然得到逐位相同的状态"。那么回溯到时刻 T 只需：

1. 从 t=0 重建一个初始状态；
2. 用**大步长**把预录的输入序列重放到 T。

不需要存任何状态，只需要存**输入序列**（极小）。

## 3. 确定性的三个前提（缺一不可）

### 3.1 前提一：固定的输入表示

输入不能是"每帧读取当前按键"，必须是**带时间戳的事件序列**：

```js
// src/app/replay.js —— 输入轨道（track）的数据结构
track = [
  { t: -3.00, key: 'ignite'  },                  // 事件类输入：带精确时刻
  { t: 12.40, key: 'pitch',   value: -0.020 },    // 连续类输入：阶跃 + 时刻
  { t: 47.85, key: 'throttle',value: 0.920 },
  { t: 175.77, key: 'sepBoosters' },              // 分离事件（由物理触发但记入轨道）
  ...
]
```

连续输入（pitchBias / throttleCmd）采用**阶跃 + 时刻**表示而非连续采样，原因是：
- 键盘输入本来就是阶跃的（按下/松开），这符合真实输入形态；
- 阶跃表示的重放是精确的，无插值误差；
- 序列长度极小 —— 一次任务通常只有几十到几百条。

### 3.2 前提二：固定步长积分 + 固定步长累加器

`src/core/sim.js` 用的是**定步长 RK4**，步长只由**仿真时间的分区**决定，与真实帧率无关：

```js
// 分区步长（constants.js）
// 大气段（h < 105 km 下行 95 km）：dt = 0.02 s   ← 需要分辨 Max-Q、跨音速
// 真空段（已入轨前）              ：dt = 0.25 s
// 滑行段（滑行 / 停泊）           ：dt = 0.5  s
```

分区切换带**迟滞**（上行 105 km 切换，下行 95 km 切换回），避免在边界上高频抖动导致步长序列不确定。

真实帧率通过**固定步长累加器**解耦：

```js
acc += dtWall * warp;
while (acc >= h) { step(h); acc -= h; }   // h 由分区决定，与 dtWall 无关
```

`dtWall` 被 `Math.min(dtWall, 0.100)` 钳位，防止切后台回来时一次性追赶上千步。

**关键点**：步长序列完全由"初始状态 + 输入序列"决定，与机器性能、帧率、显示器刷新率**无关**。

### 3.3 前提三：无隐藏的随机源

仿真内核中**不允许出现** `Math.random()`。所有看起来随机的东西必须是**确定性伪随机**：

| 位置 | 处理 |
|---|---|
| 尾焰抖动（`render.js`） | 用 `sin(t * k)` 的确定性组合，参数只依赖仿真时间 t |
| 烟雾团（`render.js`） | 每个烟团由 `(seed, t_birth)` 参数化，`seed` 是序号不是随机数 |
| 星空（`render.js`） | 固定种子的 LCG，生成一次后缓存在离屏 canvas |
| 气动/大气模型 | 完全确定性，查表 + 线性插值 |

**这一条是可验证的**：`tests/physics-audit.js` 的 I 节做了"实时推进 vs 裸重放"对比，若存在隐藏随机源，末态必然不一致。

## 4. 实现

### 4.1 `Replay.Engine`

```js
// src/app/replay.js
RK.Replay.Engine = function (opts) { ... }   // 包装一个 Sim，同时录制输入轨道
  .advance(dtWall)      // 正常推进，同时把新产生的输入追加到轨道
  .command(cmd, value)  // 玩家输入 → 同时作用于 Sim 和轨道
  .seek(T)              // 回溯：从最近检查点重放到 T
  .setTrack(track)      // 载入预录轨道（演示模式用）
```

### 4.2 检查点（Checkpoint）—— 只影响性能，不影响正确性

`CP_INTERVAL = 5`（每 5 s 仿真时间存一个精确状态点）。

**这是纯性能优化**：`seek(T)` 时从 `floor(T / 5) * 5` 处的检查点开始重放，最多只需重算 5 s 仿真时间。

> **重要澄清**：检查点**不参与正确性**。删掉所有检查点（从 t=0 裸重放）结果**逐位相同**。ADR 的 I 节测试专门验证了这一点 —— 裸全任务重放与实时推进的末态差为 `0.000e+0`。

### 4.3 安全上限

`HARD_LIMIT = 400000` 步。若一次 `seek` 超过此上限（理论上不可能，全任务仅 12516 步），抛错而非静默卡死。这是防御性编程，正常路径不会触发。

## 5. 性能实测（回答"要不要防抖/节流"）

测试环境：Node v22.22.2，Windows 11，CPU 单线程 JS。
测试方法：`tests/physics-audit.js` 第 I 节，模拟 200 次随机时刻的拖拽 `seek()`。

```
拖拽 200 次：平均 0.046 ms，中位 0.021 ms，P95 0.184 ms，最坏 0.319 ms
✓ 最坏一次 seek < 16.7 ms（60 fps 单帧预算）   → 0.319 ms
  全任务裸重放（无检查点）：8.31 ms / 12516 步
✓ 全任务裸重放 < 100 ms   → 8.31 ms
```

### 5.1 数据解读

| 场景 | 耗时 | 占 60 fps 单帧预算（16.7 ms） |
|---|---|---|
| 典型拖拽（中位） | **0.021 ms** | 0.13% |
| 平均拖拽 | 0.046 ms | 0.28% |
| P95 拖拽 | 0.184 ms | 1.1% |
| **最坏拖拽** | **0.319 ms** | **1.9%** |
| 极端情况：从 t=0 裸重放全程（无检查点） | 8.31 ms | 50% |

即便是最坏情况，也只吃掉了单帧预算的 **1.9%**，剩下 98% 留给渲染。

### 5.2 结论：**不需要防抖，也不需要节流**

`src/app/timeline.js` 的头部注释里明确写了这一点。理由：

1. 加防抖会让拖拽**手感变黏** —— 辅导员拖到某个时刻要等一下才响应，教学演示时这是明显的体验缺陷。
2. 加节流（如 `requestAnimationFrame` 合并）会把延迟从 0.3 ms 增加到最多 16 ms，**纯粹是负优化**。
3. 检查点机制已经把重算量压到最多 5 s 仿真时间，性能余量有 50 倍以上。

**唯一需要注意的**：`seek()` 只在指针拖动**真正产生新时刻**时调用（时刻秒数变化才触发），避免同一时刻重复重放。这是常量级优化，不是节流。

## 6. 与演示模式的关系

演示模式（demoMode）**完全依赖**本 ADR：

- 演示模式下玩家的物理输入被丢弃；
- 取而代之，`modes.js` 预录一条"标准操作"输入轨道；
- `timeline.js` 的 `nominal(opts)` 用 `Replay.replayTo` 预跑一遍，得到 13 个事件的标称时刻，用来画时间线刻度；
- 辅导员拖拽时，调用同一个 `seek()`，行为与挑战模式完全一致。

`nominal()` 的结果按 `targetAlt|payload|difficulty|demoMode` 缓存，避免重复计算（虽然单次只要 8 ms）。

## 7. 后果与风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 将来有人在 `sim.js` 里引入 `Math.random()` | 中 | 物理自检 I 节会立刻失败（末态不一致）；`sim.js` 头部注释已写明禁令 |
| 将来有人改成变步长积分（如 RK45 自适应） | 高 | 变步长会破坏确定性。**若确需自适应，步长必须只依赖状态而非墙钟时间**，否则本 ADR 失效 |
| 浮点非结合性导致不同机器结果不同 | 低 | IEEE 754 双精度的基本四则运算是确定性的；未用 `Math.fma`、未用 SIMD 归约；实测同机逐位一致 |
| 输入轨道过长 | 低 | 阶跃表示下一次任务仅数十至数百条；`nominal()` 有缓存 |

## 8. 验证

`tests/physics-audit.js` 第 I 节三条断言：

```
✓ 实时推进 vs 裸重放：末态最大差 < 1e-6     → 状态差 = 0.000e+0（12516 步）
✓ 两种推进方式的步数一致                    → 12516 vs 12516
✓ seek() 到任意时刻：与裸重放逐位一致（< 1e-6）→ 7 个采样点最大差 = 0.000e+0
```

**注意实测值不是"接近 1e-6"，而是精确的 0**。确定性重放在这个实现下是**逐位相同（bit-exact）**的，1e-6 只是断言的容差上限。
