## 1. 背景（Context）

`design/art/asset-spec.md` §7 给出了一张渲染技术分配表：

| 内容 | 技术 |
|---|---|
| 静态结构（箭体、整流罩、飞船） | SVG |
| 动态像素（尾焰、烟羽、拖尾、星空、地球） | Canvas |
| HUD（数字、进度条、面板） | DOM + CSS |

同时 §1.3 给出了箭体的**逐部件 SVG 规格**（精确到小数点后一位的米制尺寸）。

本 ADR 回答的问题是：**这份分配表在技术上站不站得住？如果不站得住，哪里必须改、改成什么、代价是什么？**

## 2. 决策（Decision）

**采纳 `asset-spec.md` §7 的三层分配，箭体继续走 SVG，不改用 Canvas。**

这是一条**确认性**决策而非推翻性决策 —— 也就是说，我没有把 §1.3 的内联 SVG 箭体改成 Canvas 绘制。原因如下。

### 2.1 为什么箭体必须留在 SVG（四条硬理由）

| # | 理由 | 详细论证 |
|---|---|---|
| ① | **任意缩放锐利** | 教学场景里，辅导员会在 4K 大屏上放大讲解某一级（"看这里，助推器和芯级是**同直径**的，都是 5 米"）。SVG 是矢量，缩放到 400% 依然锐利；Canvas 位图放大必然糊，除非按缩放级别动态重设 DPR 重绘整个箭体 —— 而 `asset-spec.md` §0.2 建议 DPR 封顶 2，在 4K 屏放大讲解时会不够用。 |
| ② | **主题切换零成本** | 演示模式强制浅色、挑战模式默认深色（用户决策 #1）。SVG 的描边/填充可以写成 `stroke="var(--rk-line)"`，**切换主题时 CSS 变量一改，整个箭体瞬间变色，零重绘**。Canvas 读不到 CSS 变量，必须手写调色板并在切主题时全量重绘（本项目 `render.js` 里的 `THEME` 对象就是为此存在的，见第 6 节风险 R1）。 |
| ③ | **可访问性** | `design/art/accessibility.md` §3 要求"结构可被屏幕阅读器读出"。SVG 是 DOM，节点可挂 `role` / `aria-label`；Canvas 是一张不透明位图，屏幕阅读器什么都读不到，只能额外维护一套并行的无障碍描述，等于做两遍。 |
| ④ | **分离动画走 GPU 合成** | 分离动画低频（全程 13 个事件），且形态是**纯 transform**（位移 + 旋转）。SVG 的 `<g transform>` 变化可以被浏览器提升为合成层，**CPU 几乎不出力**。若走 Canvas，每个部件的每次位移都要 CPU 重画全部路径。 |

### 2.2 关键性能澄清：SVG 的"图元数量恐惧"在这里不成立

`asset-spec.md` §7.2 提醒"SVG 节点 > 300 且每帧更新会掉帧"。**本项目不受此限制**，因为：

- `svg-rocket.js` 的 `markup()` **只在构建时执行一次**，生成静态结构；
- 运行时每帧只改 **8 个 `<g>` 的 `transform`** 和 **2 个 `class`**，图元数量再多也不参与每帧重排；
- 实测：`transform` 变化被浏览器批处理为合成操作，不触发布局（layout）和重绘（repaint）。

**结论：SVG 慢的前提是"每帧改几百个节点的属性"，而本项目每帧只改 8 个 transform。这个前提不成立。**

## 3. 为什么尾焰 / 烟羽 / 拖尾 / 星空必须走 Canvas

这四类元素有一个共同特征：**图元数量大、且每帧都要重画**。

| 元素 | 每帧图元 | 技术需求 | SVG 能否满足 |
|---|---|---|---|
| 尾焰 | 3 层 `Path2D`（核心/中层/外焰），每层 8–12 个控制点，逐帧扰动 | `globalCompositeOperation = 'lighter'` 叠加发光 + 径向渐变 | **不能**：SVG 不支持 `lighter` 合成模式（只有 `mix-blend-mode: screen`，语义不同且性能更差） |
| 烟羽 | 累积 60+ 个烟团，每个是带径向渐变的椭圆 | 逐帧 alpha 衰减、确定性参数化 | 勉强，但 60 个渐变节点每帧更新必然掉帧 |
| 弹道拖尾 | 累积 2000+ 点折线 | 逐帧追加、按相机缩放裁剪 | 勉强，2000 点的 `<polyline>` 每帧改 `points` 属性代价很高 |
| 星空 | 600 图元 | 生成一次后缓存 | 可以，但无任何收益（星空不需要交互/读出） |
| 地球 + 大气 | 采样折线 + 渐变 | 见第 4 节 | 见第 4 节 |

**决定性因素是 `lighter` 合成。** 尾焰的"发光叠加"效果（`asset-spec.md` §3.1 的核心视觉）在 SVG 里根本无法实现到同等质量。`globalCompositeOperation = 'lighter'` 会把图元颜色相加，产生高光溢出 —— 这是真火焰的视觉特征，也是这个项目在展厅大屏上"一眼看起来对"的关键。

## 4. 两个必须有的工程折中（Canvas 侧）

### 4.1 地球不能画成一个 `<circle>`

地球半径 R₀ = 6 377 300 m。在跟随相机 zoom ≈ 10 px/m 下，**半径 = 6.4 × 10⁷ 像素**。

Canvas 光栅化器面对这个量级的坐标会直接数值失效 —— 表现为画不出来、花屏，或者在某些浏览器上卡死数十秒。

**解决方案**：`_earthPath()` 不画整圆，而是**按地心角只采样屏幕上可见的那一段弧**，用折线连接。采样点数按可见弧长自适应。这样：
- 坐标量级始终在屏幕尺度内；
- 精度足够（弧段内采样步长 ≤ 2 px）；
- 无论 zoom 到多少都稳定。

### 4.2 深色 / 浅色用不同的合成模式

`asset-spec.md` §3.1 说的是深色背景下的发光叠加。但演示模式**强制浅色**（用户决策 #1），在浅色背景上用 `lighter` 会把画面**过曝成一片白** —— 尾焰和天空都烧掉，什么都看不见。

因此 `render.js` 的 `THEME` 里：

```js
dark:  { ..., composite: 'lighter'      }   // 深色：发光叠加
light: { ..., composite: 'source-over'  }   // 浅色：普通覆盖，避免过曝
```

同时浅色主题**跳过星空绘制**（白天天上看不到星星，这在教学上也更正确）。

## 5. HUD 走 DOM + CSS 的理由

HUD 的全部元素（数字、推进剂条、姿态仪、Δv 账本、轨道要素面板、字幕、时间线）都是**文本和简单形状**，且必须满足三条硬需求：

1. **数字必须等宽对齐**（`ui-spec.md` §1.3 强制 `font-variant-numeric: tabular-nums`）—— 这是 CSS 属性，Canvas 里没有；
2. **必须可被屏幕阅读器读出**（`accessibility.md` §3）；
3. **字号要能被用户放大**（设置面板里的"字号"开关）—— DOM 改一个 CSS 变量即可，Canvas 要重算所有布局。

只有一处例外：**Q / g 曲线图**用了小 Canvas，因为它是一条每帧追加的时序曲线，性质上属于"动态像素"，放在 DOM 里会污染布局。

## 6. ⚠ 需要美术复核的 4 处偏差（请 team-lead 转达 art-director / artist）

| # | 事项 | 说明 | 建议动作 |
|---|---|---|---|
| **A1** | **Canvas 读不到 CSS 变量，调色板被复制了一份** | `render.js` 顶部的 `THEME` 对象（深色/浅色各一套，约 20 个色值）与 `index.html` 里的 CSS 变量 `--rk-*` 是**两份独立维护的数据**。这是浏览器能力限制，无法避免。 | 请美术确认这两套色值当前是一致的；**今后若改 `art-bible` 配色，必须同时改这两处**，否则会出现"箭体是新的蓝、尾焰是旧的蓝"。 |
| **A2** | **浅色主题下尾焰不用 `lighter` 合成** | 见 §4.2。浅色下尾焰的"发光"观感会比深色弱，视觉上更"实"一些。 | 请美术评估浅色下的尾焰观感是否可接受；若需要，可以在浅色下改用 `multiply` 语义的暗芯 + 亮边方案，但那需要重做 §3.1 的三层路径。 |
| **A3** | **整流罩半透明剖切的实现方式** | 用户决策 #2 要求"整流罩半透明剖切，露出梦舟飞船"。实现是：整流罩拆成**左右两片**（`rk-fair-l` / `rk-fair-r`），剖切时给两片加半透明 class 并沿 `rk-seam` 虚线分开。飞船本身是**常驻绘制**的，只是平时被整流罩遮住。 | 请美术确认：① 半透明的透视比例（当前 `opacity` 值）是否合适；② 剖切时是否需要额外的"剖切边缘高光"描边，目前没有。 |
| **A4** | **描边统一用 `non-scaling-stroke`** | SVG 里用户单位 = 米，直接写 `stroke-width: 2` 会变成 **2 米粗**。所有描边元素都加了 `vector-effect="non-scaling-stroke"`，线宽恒为 2 CSS px。副作用是：**放大讲解时轮廓线不会跟着变粗**，与 `asset-spec.md` §1.3 逃逸塔"禁止 < 2 px"的要求一致，但视觉上放大后线条会显得相对更细。 | 请美术确认这个取舍可接受；若希望放大时线宽按比例增长（更像"工程图"），需要改成分档切换 `vector-effect`。 |

## 7. 图层栈（asset-spec §7.4）

```
L4  HUD 面板 / 字幕 / 时间线        DOM + CSS
L3  箭体 SVG（含整流罩、梦舟）       SVG，由 main.js 用 CSS transform 定位
L2  尾焰 / 烟羽                     Canvas   ← 必须在 L3 之下
L1  弹道拖尾                        Canvas
L0  地球 / 大气 / 星空 / 天空渐变     Canvas
```

**`L2 尾焰在 L3 箭体之下`** 是 §7.4 明确要求的，因为尾焰是从喷口向外喷、被箭体挡住一部分才对。`render.js` 的 `draw()` 里先画尾焰再由 `main.js` 摆 SVG，顺序上天然满足。

## 8. 相机对齐

两层用**同一个相机变换**对齐（`asset-spec.md` §0.1 的唯一公式）：

```
screenX = (worldX − camX) · zoom + W / 2
screenY = H / 2 − (worldY − camY) · zoom
```

Canvas 侧在 JS 里做这个变换；SVG 侧由 `render.js` 的 `rocketTransform()` 返回 `{x, y, deg, zoom}`，`main.js` 用一个 CSS `transform: translate() rotate() scale()` 摆上去。**两边共用同一份 `Camera` 对象，不存在"两套相机"**。

本项目在 §0.1 公式基础上**扩展了一个旋转 `rot = −φ`**（φ 为当地垂线相对发射点的转角）。理由：不旋转的话，火箭飞出 2000 km 后在屏幕上是斜着的，辅导员没法讲解姿态。加上旋转后，**跟随相机下当地垂线恒朝屏幕正上方**，姿态角 θ 可以直接目视读取。

## 9. 60 fps 相关

| 措施 | 位置 |
|---|---|
| DPR 封顶 2（4K 屏上再高只是徒增像素填充率） | `render.js` `resize()` |
| 星空生成一次后缓存在离屏 canvas | `render.js` `_starfield()` |
| 地球只采样可见弧段 | `render.js` `_earthPath()` |
| SVG 每帧只改 8 个 transform | `svg-rocket.js` `update()` |
| 尾焰扰动在 `reducedMotion` 下完全关闭 | `render.js` `_drawPlume()` |
| HUD 数字 10 Hz 刷新 + 300 ms 补间，非 60 Hz | `hud.js` `RateLimiter(10)` / `Tween(0, 300)` |

## 10. 后果

| 后果 | 评价 |
|---|---|
| 需要维护两套调色板（CSS 变量 + `THEME` 对象） | 已知代价，见 A1 |
| SVG 与 Canvas 的对齐依赖相机对象单一实例 | 已保证，无风险 |
| SVG 在极低端设备上合成层可能不足 | 本项目节点数受控（每帧 8 个 transform），风险低 |
